LLM Inference & the KV Cache

From prompt to streamed response: tokenization, embeddings, attention, prefill/decode, KV caching, and quantization.

You type a prompt. A few hundred milliseconds later, words start streaming back at you one at a time. Feels simple. It isn't. What happens between your keystroke and that first token is one of the most carefully engineered pipelines in modern computing.

And buried at the heart of it is a deceptively simple optimization — the KV cache — that transforms large language models from powerful-but-slow into fast, scalable, real-time systems. Once you see how it all fits together, you'll never look at a generate() call the same way again.

The Mental Model

An LLM is a neural network that predicts the next token. Just one token. Then it takes that token, sticks it onto the end of your prompt, and predicts the next one. Then repeats.

That's the whole loop.

The interesting questions are: how does it predict that next token, and why does the second token come out much faster than the first?

Step 1: Your Text Becomes Numbers

Neural networks don't read English. They read vectors. So the first thing that happens to your prompt is tokenization — your text gets chopped into pieces, and each piece is assigned an integer ID.

Most modern LLMs use a scheme called Byte Pair Encoding (BPE). The idea: start with raw characters, then merge the most common adjacent pairs over and over until you have a vocabulary of ~50,000 chunks. Common words like the get one token. Rare words like unhappiness get split into pieces like un + happi + ness.

prompt = "How does inference work?"
ids = tokenizer.encode(prompt)
# ids -> [2437, 1374, 32278, 670, 30]

This step matters more than people realize. Languages that weren't well-represented in the tokenizer's training data get chopped into more pieces — meaning more tokens, higher cost, and slower responses for the same sentence.

Step 2: Each Token Becomes a Vector

Each integer ID gets looked up in a giant matrix called the embedding table. If your model has a vocabulary of 50K and a hidden dimension of 4,096, the table has shape [50000, 4096]. Pick a row, get a vector.

# embedding_table has shape [vocab_size, hidden_dim]
vectors = embedding_table[ids]   # shape: [num_tokens, 4096]

These vectors aren't random. During training, the model nudged them so that semantically similar tokens ended up near each other in this high-dimensional space. King and queen are neighbors. Python and snake are neighbors along one axis; python and javascript along another.

The embedding layer is also where position information gets injected — because attention itself doesn't know which token came first. Modern models use schemes like RoPE that rotate the vectors based on their position in the sequence.

Embeddings place semantically similar tokens close together in high-dimensional space

Step 3: Layers of Attention

Now the real work begins. Your sequence of vectors gets fed through a stack of transformer layers — often 32 or more — one after the other. Each layer does roughly the same thing:

  • Mix information across tokens using self-attention.
  • Mix information within each token using a feed-forward network.

Self-Attention

For every token, the layer produces three new vectors by multiplying with three learned weight matrices:

# x is the input to this layer, shape [num_tokens, hidden_dim]
Q = x @ Wq  # queries
K = x @ Wk  # keys
V = x @ Wv  # values

Each token produces three views: Query, Key, and Value

Now you have three views of every token. The trick: each token uses its query to look at every other token's key, and the strength of the match decides how much of that other token's value to mix in.

raw     = Q @ K.T
scaled  = raw / sqrt(hidden_dim)  # keeps softmax stable
weights = softmax(scaled)         # one row per token, sums to 1
output  = weights @ V

Attention scores: each token decides how much to attend to every other token

That's the magic. A token decides what context it needs by looking around and pulling in whatever it finds useful. Stack 32 layers of this and you get a model that can track references across thousands of tokens.

After attention, each token's vector goes through a small feed-forward network. Attention moves information around. The feed-forward network processes it.

Step 4: Predict the Next Token

After the final layer, the model takes the vector for the last position, projects it back to vocabulary size, and applies softmax to get a probability over every possible next token. Sample from that distribution, and you have your first generated token.

Now we hit the interesting part.

The Two Phases Nobody Tells You About

Generating a 200-token response isn't one task — it's two tasks that look nothing alike under the hood.

Prefill and decode: same model, same hardware, completely different bottlenecks

Prefill

All input tokens processed in parallel. GPU is doing massive matrix math — compute-bound.

Bottleneck: TTFT
Phase 2
Decode

One token generated per step. GPU waits on memory to load weights and cache — memory-bound.

Phase 1: Prefill

When you submit a prompt, the model processes all your input tokens in parallel. Every token's Q, K, and V get computed at the same time. Attention runs as a big matrix-by-matrix multiplication.

GPUs love this. Matrix-matrix multiplication is what they were built for. The bottleneck here is raw arithmetic throughput — the GPU is pinned at high utilization, doing math as fast as the silicon allows. The metric is Time to First Token (TTFT) — the idle time before the first word shows up on your screen.

# Prefill: process the whole prompt in one shot
hidden = embed(prompt_tokens) + positions
for layer in model.layers:
    Q, K, V = project(hidden)             # for ALL tokens at once
    hidden  = attention(Q, K, V) + hidden
    hidden  = feedforward(hidden) + hidden
    cache_kv(layer, K, V)                 # save K and V for later
first_token = sample(project_to_vocab(hidden[-1]))

Phase 2: Decode

Once the first token is out, the model switches modes. To generate token 51, it only needs to compute Q, K, and V for that one new token. The previous 50 tokens? Their K and V vectors haven't changed. Recomputing them would be wasted work.

During decode, only the new token's Q is computed; cached K and V handle the rest

# Decode: one token per iteration
token = first_token
steps = 0
while token != STOP and steps < MAX_STEPS:
    x = embed(token) + position(steps)
    for layer in model.layers:
        q, k, v = project(x)
        K_all, V_all = caches[layer].append(k, v)  # cached history + new
        x = layer.forward(q, K_all, V_all, x)
    token = sample(project_to_vocab(x))
    steps += 1
    yield token

Instead of multiplying a matrix of queries against a matrix of keys, you're multiplying a single query vector against a matrix of keys. The arithmetic is tiny — but the GPU still has to load every weight matrix and every cached K and V from memory. Suddenly the bottleneck flips. The chip has plenty of compute headroom and is just waiting for memory to deliver data.

The metric here is Inter-Token Latency (ITL) — the gap between consecutive tokens streaming out. Low ITL is what makes a model feel fast.

KV Cache: The Optimization That Makes This All Viable

What Is KV Cache?

KV cache (Key-Value Cache) is a technique used in transformer-based models to avoid recomputing attention for tokens that have already been processed. In a transformer, every token attends to every previous token using keys (K) and values (V) — derived from the input tokens and used repeatedly during generation.

Instead of recalculating K and V for past tokens every time a new token is generated, the model stores (caches) them. That stored data is the KV cache.

Why It Matters

Without KV cache, generating a sequence of length n requires recomputing attention over all previous tokens at every step — O(n²) time complexity, high latency, and wasted computation. With KV cache, generation becomes linear O(n) instead of quadratic. It's the reason LLMs can respond in real time instead of slowing down exponentially.

How It Works (Step by Step)

At each decoding step:

  1. The model receives a new token.
  2. It computes Query (Q), Key (K), and Value (V) for that new token.
  3. Instead of recomputing K and V for all previous tokens, it retrieves cached K and V.
  4. Attention is computed as: Q (new token) × K (all cached tokens).
  5. The new K and V are appended to the cache.
class KVCache:
    def __init__(self):
        self.K = None  # all keys seen so far,   shape [tokens, dim]
        self.V = None  # all values seen so far, shape [tokens, dim]

    def append(self, k_new, v_new):
        if self.K is None:
            self.K, self.V = k_new, v_new  # first token
        else:
            self.K = concat([self.K, k_new], axis=token_axis)
            self.V = concat([self.V, v_new], axis=token_axis)
        return self.K, self.V  # full history so far
Intuition: Imagine generating "The future of AI is…" word by word. Without KV cache, every new word forces recomputation of all previous words. With KV cache, the model remembers previous computations and builds on them. That's why streaming responses feel fast and smooth.

The Speedup — and the Price

The speedup is huge — think 5× or more for long generations. But there's a cost: the cache lives in GPU memory, and it grows with every token. Every layer keeps its own K and V tensors. For a 13B model, roughly 1 MB per token. A 4K-token context burns through ~4 GB of VRAM just on the cache.

This is why long contexts feel slow and expensive. It's not the model running out of brainpower — it's the cache running out of room.

Trade-offs and Challenges

Memory Usage

KV cache grows with sequence length. For long contexts, it can consume enormous GPU memory. Cache size is directly tied to the maximum context window — longer contexts mean a larger cache.

Batch Complexity

Handling KV cache across multiple sequences in parallel is tricky and requires careful memory management.

Context Limits

As context windows expand (to 128K, 1M tokens), managing the cache becomes an increasingly central engineering challenge.

Optimizations Around KV Cache

Modern systems use several techniques to make KV caching more efficient:

  • Paged KV Cache (PagedAttention): Memory is allocated in chunks, like an OS paging memory. Used in systems like vLLM.
  • Quantized KV Cache: Reduce precision (e.g., FP16 → INT8 or INT4) to shrink memory footprint.
  • Eviction Strategies: Drop less important tokens during very long contexts using sliding window approaches.
  • Flash Attention: Efficient attention computation with better memory handling, reducing the cost of large K and V matrices.
  • Grouped-Query Attention (GQA): Share K and V across multiple attention heads to reduce cache size.

Frontier Research: Shrinking the Cache Itself

Quantization and paging treat the cache as a fixed cost. Some recent architectures go further — redesigning attention so the cache is small from the start.

DeepSeek V4: redesigning attention itself to minimize the KV cache

DeepSeek's V4 series (previewed in late 2025) uses a hybrid scheme combining two compressed attention variants — one sparse, one dense — both operating on a heavily compressed KV stream. At a one-million-token context, V4-Pro reports around 10% of the cache size and 27% of the per-token compute of its predecessor.

The takeaway isn't the specific architecture. It's that the KV cache has become the bottleneck the field is now optimizing the model around. When attention itself is being redesigned to minimize the cache, you know the constraint has fundamentally shifted.

Quantization: Trading Bits for Speed

Training needs precision. Inference often doesn't. Most production deployments run in FP16 or BF16 instead of FP32, which halves memory and roughly doubles throughput on Tensor Cores. Aggressive setups go further, quantizing weights to INT8 or even INT4.

Putting It All Together

Here's the full journey of one prompt, end to end:

  1. Tokenize. Text becomes integer IDs.
  2. Embed. IDs become vectors. Position information gets folded in.
  3. Prefill. Every layer runs over every input token in parallel. Compute-bound. The KV cache gets populated. First output token pops out.
  4. Decode loop. For each new token: compute Q for just the new token, attend over all cached K and V, run the feed-forward network, sample. Append the new K and V to the cache. Memory-bound. Repeat.
  5. Detokenize. Token IDs get mapped back to characters and streamed to your screen.

Modern serving frameworks like vLLM, TensorRT-LLM, and Text Generation Inference wrap this loop with continuous batching (tokens from multiple users get interleaved on the same GPU step), speculative decoding (a small model drafts tokens, the big model verifies), and clever memory management. That's how a single GPU serves dozens of concurrent users.

Modern serving frameworks layer continuous batching and speculative decoding on top of the inference loop

What This Should Change About How You Think

  • Long prompts are expensive in TTFT; long outputs are expensive in ITL. They stress different things. Optimize for the one your users actually feel.
  • Context length isn't free. Doubling it doesn't just double compute — it bloats the KV cache and starves your batch size.
  • Quantization is the highest-leverage knob you have. Going FP16 → INT8 often cuts latency in half with negligible quality loss.
  • GPU utilization can be misleading. A model that pegs the GPU during prefill might sit at 30% during decode. The fix isn't more compute — it's faster memory or a smaller cache.
  • KV cache is the hidden engine. It transforms transformers from powerful-but-slow into fast, scalable, real-time systems.

The transformer architecture gets all the attention, but inference performance lives or dies on the boring stuff: memory layout, cache management, bit widths. The art is squeezing the most from the hardware you've got.

Now when someone tells you their model is slow, you'll know which question to ask first: is it slow to start, or slow to stream?
