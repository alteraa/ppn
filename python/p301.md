## 1. Functions as First-Class Objects

---

### 1.1. Treating a Function Like an Object

* Functions in Python are **first-class objects**, meaning they can:
  * Be created at runtime.
  * Be assigned to variables.
  * Be passed as arguments.
  * Be returned from functions.

* Functions have attributes like `__doc__`, which can be used to generate documentation.
  * Example:
  ```python
  def factorial(n): return 1 if n < 2 else n * factorial(n - 1)
  fact = factorial
  list(map(factorial, range(11)))  # Demonstrates passing function to another function
  ```

---

### 1.2. Higher-Order Functions

* A **higher-order function** is one that takes another function as an argument or returns a function.
* Examples:

  * `sorted(fruits, key=len)` sorts words by length.
  * `sorted(fruits, key=lambda word: word[::-1])` sorts by reversed spelling.
* Deprecated: `apply()` was removed in Python 3. Use `fn(*args, **kwargs)` instead.

---

### 1.3. Modern Replacements for `map`, `filter`, and `reduce`

* List comprehensions and generator expressions are now preferred over `map` and `filter` for clarity.

  ```python
  [factorial(n) for n in range(6)]
  [factorial(n) for n in range(6) if n % 2]
  ```
* `reduce` is no longer a built-in function; it is now in `functools`.

  ```python
  from functools import reduce
  reduce(add, range(100))
  sum(range(100))  # Preferred alternative
  ```
* Other reducing functions:

  * `all(iterable)`: True if all elements are truthy.
  * `any(iterable)`: True if any element is truthy.

---

### 1.4. Anonymous Functions

* Python’s `lambda` lets you define short anonymous functions.

  * Syntax: `lambda x: x + 1`
  * Used mostly in arguments to higher-order functions.

  ```python
  sorted(fruits, key=lambda word: word[::-1])
  ```
* If the lambda is too complex, refactor it using `def`.

---

### 1.5. The Nine Flavors of Callable Objects

* Python objects that can be called like functions:

  1. **User-defined functions**
  2. **Built-in functions** (e.g., `len`)
  3. **Built-in methods** (e.g., `dict.get`)
  4. **Instance methods**
  5. **Classes** (call creates a new instance)
  6. **Class instances** (if `__call__` is defined)
  7. **Generator functions** (`yield`)
  8. **Native coroutine functions** (`async def`)
  9. **Async generator functions** (`async def` with `yield`)
   
* Use `callable(obj)` to test if an object is callable.

---

### 1.6. User-Defined Callable Types

* You can make any class instance callable by implementing `__call__`.

  ```python
  class BingoCage:
      def __call__(self): return self.pick()
  ```
* Useful for keeping internal state, decorators, and memoization.

---

### 1.7. From Positional to Keyword-Only Parameters

* Python functions support flexible parameter declarations:

  * `*args`: captures extra positional arguments.
  * `**kwargs`: captures extra keyword arguments.
  * Keyword-only arguments must be defined after `*` in the parameter list.

    ```python
    def tag(name, *content, class_=None, **attrs):
    ```

---

### 1.8. Positional-Only Parameters

* Introduced in Python 3.8.
* Use `/` to mark parameters as **positional-only**.

  ```python
  def divmod(a, b, /): ...
  def tag(name, /, *content, class_=None, **attrs): ...
  ```

---

### 1.9. Packages for Functional Programming

_The `operator` Module_

* Provides function equivalents for common operators:
  * Example: `operator.mul` instead of `lambda a, b: a * b`
  * Useful for replacing lambdas with readable function calls.
  
  ```python
  reduce(mul, range(1, n+1))
  ```
* `itemgetter`: Fetch item(s) by index from objects (e.g., for sorting).
  
  ```python
  sorted(data, key=itemgetter(1))
  ```
* `attrgetter`: Fetch attribute(s) from objects, including nested attributes.
  
  ```python
  sorted(metro_areas, key=attrgetter('coord.lat'))
  ```
* `methodcaller`: Creates functions that call a method with preset arguments.
  
  ```python
  methodcaller('replace', ' ', '-')('a b')  # -> 'a-b'
  ```
---

_The `functools.partial` Function_

* Allows **pre-filling** some arguments of a function.

  ```python
  triple = partial(mul, 3)
  triple(7)  # -> 21
  ```
* Example: pre-configure an HTML tag generator

  ```python
  picture = partial(tag, 'img', class_='pic-frame')
  ```

---

### 1.10. Chapter Summary

* Functions in Python are fully **first-class citizens**.
* Python supports **higher-order functions**, **closures**, and **anonymous functions**.
* **Callable objects** are diverse and powerful, thanks to Python’s object model.
* The language includes built-in support for **functional programming patterns** through modules like `operator` and `functools`.
* New syntax like **positional-only** and **keyword-only** parameters adds flexibility to function definitions.
* Tools like `partial`, `itemgetter`, and `methodcaller` help avoid complex lambdas and promote cleaner code.

## 2. Type Hints in Functions

---

### 2.1. Introduction to Type Hints

* Type hints were introduced in **PEP 484** to support static analysis tools (like Mypy) without affecting Python's dynamic nature.
* Python remains a dynamically typed language; type hints are **optional**, not mandatory.
* Type hints help catch bugs in **large-scale or professional codebases**, especially in **IDEs and CI pipelines**.
* Less useful for small-scale, exploratory, or educational scripts.

---

### 2.2. Gradual Typing

* Python's type system is **gradual**:

  * **Optional**: Type hints can be added incrementally.
  * **Non-enforcing**: Type hints do not raise runtime errors.
  * **Do not affect performance**: No runtime optimization based on hints.
* The `Any` type acts as a wildcard, compatible with all types and operations.

---

### 2.3. Gradual Typing in Practice with Mypy

* Mypy is a static type checker used to validate Python type hints.
* Default behavior:

  * Ignores unannotated functions.
* Adding type hints incrementally:

  ```python
  def show_count(count: int, word: str) -> str:
  ```
* Use Mypy flags:

  * `--disallow-untyped-defs` (strict)
  * `--disallow-incomplete-defs` (gentle, incremental)

---

### 2.4. Using `None` as a Default and `Optional`

* If a parameter might be `None`, use `Optional`:

  ```python
  def show_count(count: int, singular: str, plural: Optional[str] = None) -> str:
  ```
* `Optional[str]` is equivalent to `Union[str, None]`.

---

### 2.5. Types Are Defined by Supported Operations

* Duck Typing: Python only cares about whether an object **supports certain operations**, not its declared type.
* Nominal Typing: Type checkers (like Mypy) rely on the **declared type**, not runtime behavior.
* Example:

  ```python
  def double(x): return x * 2
  ```

  * Works for many types at runtime.
  * Type checkers reject it if `x: Sequence` because `Sequence` lacks `__mul__`.

---

### 2.6. Duck Typing vs. Nominal Typing

* Duck Typing:

  * Flexible, runtime only.
  * May cause late detection of bugs.
* Nominal Typing:

  * Statically enforced.
  * Catches potential bugs early but may reject valid runtime behavior.
* Example:

  ```python
  class Bird: pass
  class Duck(Bird): def quack(self): ...
  def alert_bird(birdie: Bird): birdie.quack()  # Type error in Mypy
  ```

---

### 2.7. Type Annotations: Core Types

* `Any`
  * Assumed by default for untyped variables/functions.
  * Accepts and supports all operations.
  * Not safe for strict type checking.

* Simple Types
  * Use built-in types directly: `int`, `str`, `float`, `bool`.

* `Optional` and `Union`
  * `Optional[str]` = `Union[str, None]`
  * Use `str | None` syntax in Python 3.10+.

* Generic Collections
  * Use `list[str]`, `set[int]`, etc.
  * Before Python 3.9, use `List[str]` from `typing`.

---

* Tuples
  * **Fixed size**: `tuple[str, int]`
  * **Named**: `NamedTuple`
  * **Variable length**: `tuple[int, ...]`

* Mappings
  * `dict[str, int]` or `Mapping[str, int]` (preferred for parameters).

* Abstract Base Classes (ABCs)
  * Prefer ABCs (`Mapping`, `Sequence`) for parameter annotations to allow broader input types.


---

### 2.8. TypeVar and Generic Functions

* Use `TypeVar` to define flexible, generic functions.

  ```python
  T = TypeVar('T')
  def sample(data: Sequence[T]) -> list[T]: ...
  ```

* Restricted `TypeVar`

  * Limit allowed types:

    ```python
    NumberT = TypeVar('NumberT', float, Decimal, Fraction)
    ```

* Bounded `TypeVar`

  * Ensure types are subclasses of a base:

    ```python
    HashableT = TypeVar('HashableT', bound=Hashable)
    ```

---

### 2.9. Protocols for Static Duck Typing

* Introduced in Python 3.8 via `typing.Protocol`.
* Define required methods, without inheritance.

  ```python
  class SupportsLessThan(Protocol):
      def __lt__(self, other: Any) -> bool: ...
  ```

* Example with `top()` function:
  * Returns top N sorted elements.
  * Type must support `<` operator, ensured via protocol.

---

### 2.10. Style, Tools, and Gotchas

* Use **flake8**, **blue**, or **black** for code formatting and style.
* Common mistake:

  ```python
  def hex2rgb(color=str) -> tuple[int, int, int]  # Incorrect
  ```

  * `color: str` is correct; `color=str` sets default value, not type.


---

### 2.11. Chapter Summary

* Type hints (PEP 484) are optional annotations for static analysis; they do not affect runtime or performance.
* Python supports gradual typing: hints can be added incrementally, and the `Any` type acts as a universal wildcard.
* Static checkers like Mypy validate type hints and can be configured for strictness.
* Use `Optional` for parameters that may be `None`; `Optional[X]` is the same as `Union[X, None]`.
* At runtime, Python uses duck typing (based on behavior), but static checkers use nominal typing (based on declared types).
* Core annotations include built-in types, `Optional`, `Union`, generic collections, tuples, and abstract base classes (ABCs).
* Prefer ABCs (e.g., `Mapping`, `Sequence`) for parameters to allow flexible input types.
* `TypeVar` enables generic functions, with options to restrict or bound types.
* Protocols (`typing.Protocol`) support static duck typing by specifying required methods.
* Use code formatters and linters for style; avoid confusing type hints with default values.

## 3. Decorators and Closures

---

### 3.1. Decorators 101

* A **decorator** is a callable that takes another function as an argument and returns either the same function or a replacement.
* Syntax:

  ```python
  @decorate
  def target(): ...
  ```

  is equivalent to:

  ```python
  def target(): ...
  target = decorate(target)
  ```
* Example shows `target` becomes an alias for `inner`, showing the original function is replaced.

* **Key facts**:
  * A decorator is a function or callable.
  * It may replace the decorated function.
  * It executes immediately at module load time.

---

### 3.2. When Python Executes Decorators

* Decorators are executed as soon as the function is defined — typically during **import time**, not **runtime**.
* In Example 9-2:

  * A `register` decorator adds functions `f1`, `f2` to a `registry` list.
  * Output shows `register()` calls before main function runs.
* Highlight: Decorators alter behavior as the module is being loaded.

---

### 3.3. Registration Decorators

* Real-world decorators are often defined in separate modules and used across others.
* Many frameworks use such decorators for **URL routing**, **command registration**, etc.
* Even simple decorators that don’t change functions (like `register`) have real applications.

---

### 3.4. Variable Scope Rules

* Python assumes variables assigned in a function are **local**, even if assignment is after reference.
* Examples:

  * Referring to `b` before assignment in the same function causes `UnboundLocalError`.
* `global` can override this to refer to module-level variable.
* Variable scopes:

  * Local (function)
  * Global (module)
  * Nonlocal (enclosed function scope – covered next)

---

### 3.5. Closures

* A **closure** is a function that remembers the environment in which it was created.
* It retains access to **free variables** from an outer function even after the outer function is gone.
* Example 9-8:

  * `make_averager()` returns a nested `averager()` that keeps appending to a list (`series`) from the enclosing scope.
* Inspection:

  * Free variables are stored in `__closure__`.
  * Example shows how `series` persists across calls.

---

### 3.6. The `nonlocal` Declaration

* With **immutable types** (like integers), assigning inside a nested function makes them **local** by default, breaking the closure.
* `nonlocal` allows a nested function to modify a variable in an enclosing scope.
* Example 9-13 shows how `nonlocal count, total` fixes a broken average calculator.

---

### 3.7. Variable Lookup Logic

* Rules for resolving variable names:

  * If declared `global`: from module global scope.
  * If declared `nonlocal`: from the nearest enclosing function.
  * If assigned: local.
  * If only referenced:

    * Search nonlocal scopes → global → built-ins.

---

### 3.8. Implementing a Simple Decorator

* Example: `clock` decorator logs call time and result.
* Uses `*args` to wrap functions of any arity.
* Decorator replaces the original function with the wrapper `clocked`.

---

### 3.9. Improving Decorators with `functools.wraps`

* `@functools.wraps(func)`:

  * Preserves metadata like `__name__`, `__doc__`.
  * Also supports keyword arguments with `**kwargs`.
* Recommended best practice for writing clean decorators.

---

### 3.10. Decorators in the Standard Library

* Built-in decorators:

  * `@property`, `@staticmethod`, `@classmethod`
* `functools` module provides:

  * `@wraps`
  * `@cache`
  * `@lru_cache`
  * `@singledispatch`

---

### 3.11. Memoization with `functools.cache`

* Python 3.9+: `@cache` stores results of function calls with hashable arguments.
* Used to speed up recursive functions like Fibonacci.
* Example:

  ```python
  @functools.cache
  @clock
  def fibonacci(n): ...
  ```
* Note: All arguments must be **hashable**.

---

### 3.12. Using `lru_cache`

* `@lru_cache(maxsize=128, typed=False)`:

  * Caches results with LRU eviction policy.
  * Works in Python 3.2+.
* Allows fine-tuned memory management.
* `typed=True` treats different types as different keys (e.g., `1` vs `1.0`).

---

### 3.13. Single Dispatch Generic Functions

* `@singledispatch` turns a function into a generic dispatcher based on the **first argument’s type**.
* Use `.register()` to add implementations:

  ```python
  @htmlize.register(str)
  def _(text): ...
  ```
* Supports custom and third-party types.
* Encourages **modular extension** and decouples logic.

---

### 3.14. Parameterized Decorators

* To make a decorator accept parameters, wrap it in a **factory**:

  ```python
  def register(active=True):
      def decorate(func): ...
      return decorate
  ```

  Then use:

  ```python
  @register(active=False)
  def f1(): ...
  ```

---

### 3.15. The Parameterized Clock Decorator

* Adds format string control:

  ```python
  @clock('{name}({args}) dt={elapsed:0.3f}s')
  def snooze(seconds): ...
  ```
* Uses `locals()` to inject values into the format.
* Demonstrates nesting: `clock()` → `decorate()` → `clocked()`.

---

### 3.16. A Class-Based Clock Decorator

* Alternative implementation using a class with `__call__`.
* Easier to maintain for complex decorators:

  ```python
  class clock:
      def __init__(self, fmt): ...
      def __call__(self, func): ...
  ```

---

### 3.17. Chapter Summary

* Reviewed the decorator mechanism from basic to advanced:

  * Simple registration
  * Closures and variable scoping
  * `nonlocal` usage
  * Caching and generic dispatch
  * Parameterized decorators
* Emphasized use cases: metaprogramming, functional callbacks, modular design
* Concluded with best practices and more maintainable class-based decorators.

## 4. Design Patterns with First-Class Functions

---

### 4.1. Introduction

* **Design patterns** are general, reusable solutions to common problems in software design.
* The book “Design Patterns” (by the “Gang of Four”) presents 23 patterns mostly in C++.
* Some of these patterns are unnecessary or overly complex in dynamic languages like Python.
* Peter Norvig noted that **16 of 23** patterns become *simpler or invisible* in dynamic languages.
* This chapter shows how **first-class functions** simplify patterns like Strategy and Command.


---

### 4.2. Case Study: Refactoring Strategy

* Classic Strategy

  * **Intent**: Define a family of algorithms, encapsulate each one, and make them interchangeable.
  * Common in ecommerce systems (e.g., applying different discount strategies to orders).
  * Three discount rules:

    1. 5% for customers with ≥ 1000 fidelity points.
    2. 10% for each item with ≥ 20 units.
    3. 7% for orders with ≥ 10 distinct items.
  * Structure:

    * `Order`: the *context* that delegates discount computation.
    * `Promotion`: abstract base class (strategy interface).
    * `FidelityPromo`, `BulkItemPromo`, `LargeOrderPromo`: concrete strategy classes.
  * Example usage shows passing a strategy instance to the `Order` class.
  
---

* Function-Oriented Strategy
  * Refactors strategy classes into simple **functions**.
  * The `promotion` field in `Order` now accepts a callable: `Callable[[Order], Decimal]`.
  * Each strategy is a standalone function:

    * `fidelity_promo(order)`
    * `bulk_item_promo(order)`
    * `large_order_promo(order)`
  * Benefits:

    * Less boilerplate.
    * Easier to reuse and test.
    * No need to instantiate classes.
  * `Order.due()` calls `self.promotion(self)`—requires passing `self` because `promotion` is not a method.

---

### 4.3. Choosing the Best Strategy: Simple Approach

* Goal: Automatically choose the best available promotion.
* Define `best_promo(order)` that applies all strategies and picks the one with the highest discount.
* Strategies are stored in a list:

  ```python
  promos = [fidelity_promo, bulk_item_promo, large_order_promo]
  ```

  Then:

  ```python
  def best_promo(order):
      return max(promo(order) for promo in promos)
  ```

---

### 4.4. Finding Strategies in a Module

* Using `globals()`

  * Uses `globals()` to find all functions ending in `_promo`.
  * Builds the `promos` list dynamically:

    ```python
    promos = [promo for name, promo in globals().items()
              if name.endswith('_promo') and name != 'best_promo']
    ```

* Using a Separate Module and `inspect`
  * Stores strategies in a module (e.g., `promotions.py`).
  * Uses `inspect.getmembers` to find functions:

    ```python
    import promotions
    promos = [func for _, func in inspect.getmembers(promotions, inspect.isfunction)]
    ```
  * More robust and scalable than `globals()` approach.

---

### 4.5. Decorator-Enhanced Strategy Pattern

* Uses a **decorator** to register strategy functions:

  ```python
  promos = []

  def promotion(promo):
      promos.append(promo)
      return promo
  ```
* Decorated functions automatically added:

  ```python
  @promotion
  def fidelity(order): ...
  ```
* Advantages:

  * No need for naming conventions.
  * Promos can be defined anywhere.
  * Easy to disable promotions (comment out the decorator).

---

### 4.6. The Command Pattern

* Command decouples invokers from receivers using objects that encapsulate requests.
* In classic form, requires classes with a single `execute` method.
* Simplified in Python using **functions**:
  * Pass a function to the invoker instead of a Command object.
  * Call `command()` instead of `command.execute()`.
* Example: `MacroCommand` A callable class holding a list of commands (functions):
    ```python
    class MacroCommand:
        def __init__(self, commands):
            self.commands = list(commands)

        def __call__(self):
            for command in self.commands:
                command()
    ```
  * Useful when:
    * Need stateful commands.
    * Need undo functionality.
    * Can use closures or callables with `__call__`.

---

### 4.7. Chapter Summary

* Many classic OOP design patterns are simpler in Python due to first-class functions.
* Strategy and Command patterns often involve:

  * Single-method interfaces (`execute`, `run`, etc.)
  * Can be replaced with plain functions or callable objects.
* Functions are:

  * Lightweight.
  * Reusable.
  * Naturally support shared usage (like Flyweight).
* Python’s features allow for **less boilerplate** and more **concise, expressive** code.
